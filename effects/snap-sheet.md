## 1 一句话

同一个底部面板停在三档高度上（35% / 62% / 全开），拖动时按「位移 + 速度」一起决定落到哪一档。

## 2 交互问题

**两态面板会逼用户做一次它不该做的决定。** 「开」和「关」之间其实常常有中间态：看地图时
想知道附近有什么（35%），想看清列表（62%），想看全（全开）。只有两态的话，用户只能在
"挡住半屏"和"什么都没有"之间跳。

第二个问题更细：**档位不是"拖到哪个高度就停在哪"**，而是"松手时判断你想去哪"。
慢慢拖到 50% 高度松手，落点是 62% 还是 35%，取决于最近的那个——但轻轻一甩，
即使只拖了 15%，也应该跨到下一档。这就是为什么速度不参与"距离阈值"，而是改变**落点本身**。

## 3 手感来源

| 取什么 | 丢什么 |
|---|---|
| Vaul 的 snapPoints：档位是「可见高度比例」，不是绝对像素 | Vaul 的滚动容器接管与内部滚动联动（面板滚到底再拖收起） |
| 速度把落点**往前投影**再取最近档 —— 一套数学覆盖"慢慢拖"和"轻甩" | 「甩得够快直接关掉」当作独立阈值（那种写法在两档之间会误判） |
| 在最低档往下轻甩就关（单独一条判定） | 面板圆角/阴影随档位渐变（iOS 有） |
| 档位间迁移只写 `transform`，遮罩不跟手 | 遮罩随档位微调透明度（会让最低档读起来像"快关了"） |

## 4 参数与为什么

| 参数 | 值 | 为什么是这个值 |
|---|---|---|
| 档位单位 | 面板自身高度的比例 | 面板高度是内容驱动的（`max-height: 82dvh` 只是上限）。用视口比例会在内容少的面板上算出不一致的档 |
| 默认档位 | `[0.35, 0.62, 1]` | 35% 够看到三行（"附近有什么"）；62% 是"正在读列表"；1 = 遮罩消失、内容全见 |
| 速度投影窗口 `carry` | `160ms` | 0.55 px/ms 的甩速 × 160ms ≈ 88px，相当于"再往前多拖半个拇指"。低于 100ms 甩不动，高于 250ms 会跨两档 |
| 最低档甩出阈值 | 复用 `velocityThreshold` 0.55 px/ms | 和收起判定同一个数。用户感受到的"甩一下"只有一个强度，不该有第二套标尺 |
| 档位迁移时长 | `--mk-dur-4` = 380ms | 跨档是一次"层面切换"，不是微调。240ms 会显得被拽过去，560ms 像在等 |
| 最低档可见比例 | 0.35 | 低于 30% 抓手会和底部安全区打架；高于 40% 就挡掉太多内容，失去"半开"的意义 |

## 5 实现落点

```
gesture.js:32    offsetForSnap(visible, height)     纯函数：可见比例 → 位移
gesture.js:55    snapIndexAt(offset, h, snaps, v)   纯函数：落点 + 速度投影 → 档位下标
gesture.js:150   snapShouldClose(...)               纯函数：这一下该不该关（含"最低档甩一把"）
gesture.js:187   sheet(el, { snapPoints, snap, onSnap, dismissible })
mobile.css:110   .mk-sheet                          基础位置；有档位时由 demo 覆盖 transform
```

**三个纯函数 + 一个接线层。** 所有判断都能单测（8 条测试覆盖），`sheet()` 只做
"把指针位移喂进去、把结果写回 DOM"。这条分工和 `shouldDismiss` / `shouldGoBack` 一致。

有档位时 `sheet()` 多两个状态：

```
idx    当前档位下标
rest() 当前档位对应的位移 —— 每次现算，不缓存
```

`rest()` 现算不缓存是必需的：Vue 指令 `mounted` 时节点可能还没布局，`offsetHeight` 是 0，
缓存下来的位移会永远停在 0，面板一打开就在最顶上。

## 6 降级契约

**走 `mobile.css` 那档：减。**

```css
@media (prefers-reduced-motion: reduce) {
  .mk-sheet { transition-duration: 120ms; }
  @starting-style { .mk-sheet { transform: none; opacity: 0; } }
}
```

档位逻辑不摘 —— 它是**功能**（用户要能选择看多少内容），和"动效"不是一回事。
减弱动效时只把跨档的 380ms 压到 120ms：档位还是那三档，只是过去得更快。

拖拽手势本身也保留：减弱动效的用户一样要把面板拖起来看全。

## 7 容易做错的地方

**① 别在构造时缓存档位位移。**

```js
// 错：mounted 时 offsetHeight 可能是 0
let rest = offsetForSnap(snaps[idx], el.offsetHeight);

// 对：用到时再算
const rest = () => (snaps ? offsetForSnap(snaps[idx], height()) : 0);
```

实测过这个坑：`v-show` 控制的节点在 `mounted` 那一刻 `display: none`，`offsetHeight` 返回 0，
`rest` 被算成 0，面板一打开就直接贴在最顶上（全开档），和声明的初始档无关。

**② 速度不能替换距离判定，要参与"落点计算"。**

错误直觉是"拖得够远 → 下一档；甩得够快 → 下一档"，两个条件并列。这样在两档之间
会同时命中或都不命中。正确做法是把落点往前投影：

```js
const projected = clamp(offset + velocity * carry, 0, height);
// 然后在 projected 上取最近档
```

一套最近邻数学同时覆盖"慢慢拖"和"轻甩"，不需要 if 分叉。

**③ 最低档到关闭档之间要单独判一次速度。**

最低档 0.35、关闭是 1.0，两者位移差 0.65 × 高度 = 约 390px。只靠投影要甩到
**0.66 px/ms** 才能跨过中点 —— 而 iOS 上"在最低档往下轻轻一甩就关"是肌肉记忆，
那个动作在投影里永远差一点，结果就是"甩了没反应"。所以：

```js
velocity > velocityThreshold && offset >= lowest - 1   // 宽容 1px 的浮点误差
```

这条是实测发现的：初版只有投影，从最低档 0.5 px/ms 甩下去只回到 35%，不关。

**④ 有档位时遮罩不能跟手变淡。**

无档位的 `sheet()` 里 `opacity = 1 - y / (h * 1.5)` 是对的：拖到一半遮罩半透明，
用户从遮罩就知道"我快把它关掉了"。但有档位时，从 62% 拖到 35% 也是往下拖 ——
遮罩跟着变淡会让**最低档看起来像"快关了"，而它其实是个稳态**。

正确做法：有档位时遮罩只在真正关闭时变（`.is-closing` 那条 CSS）。

**⑤ `dismissible: false` 时不能让"关闭档"参与最近邻。**

如果调用方明确说"这面板不能关"，虚拟关闭档就必须从候选里去掉，否则
"拖得很远"会落到一个不存在的档上。`snapIndexAt` 的 `dismissible` 参数就是干这个的；
`sheet()` 里先判 `snapShouldClose`（它会尊重 `dismissible`），再用
`dismissible: false` 取档位——顺序反了会得到"该关但关了没关"的矛盾状态。

**⑥ 档位顺序由调用方给，但必须自己再排一次。**

`[1, 0.35, 0.62]` 和 `[0.35, 0.62, 1]` 是同一组档位，但下标语义完全不同
（`snap: 1` 指的是第二档）。`sheet()` 里做一次 `sort()` 并约定"下标从低到高"，
调用方就不用记规则。代价是**调用方传 `snap` 时必须按排序后的顺序数**——
这一条写进 JSDoc，否则第一次用必踩。

## 8 AI 提示词

**用途**：在别的项目里实现同一个多档面板。

```text
实现一个多档位底部面板（snap points）。原生 Pointer Events + CSS 过渡，不引依赖。

原理一句话：档位是一组固定的位移落点，松手时把"当前位移 + 速度×一小段时间"投影成一个落点，
再取最近的档 —— 一套最近邻数学同时覆盖"慢慢拖"和"轻甩"。

结构：
  <div class="backdrop"></div>
  <div class="sheet" style="max-height: 82dvh">
    <div class="grabber" data-handle></div>
    ...内容...
  </div>

档位用「面板自身可见高度的比例」表示，升序，例如 [0.35, 0.62, 1]。
位移 = 高度 × (1 − 比例)：全开 0，完全收起 = 高度。

单指针拖动（只接主键 e.button === 0），pointerdown 时调 setPointerCapture，
这样手指移出元素也继续收到 move。

拖动中：transform = translate3d(0, clamp(当前档位移 + dy, 0, 高度), 0)，
并且该元素 transition: none。

松手：
1. 若是 pointercancel → 不做任何判定，直接滑回当前档（浏览器抢走手势不是用户松手）。
2. 若 velocity > 0.55 px/ms 且当前位移已到最低档（容差 1px）→ 关闭。
3. 否则取档：
     projected = clamp(offset + velocity * 160, 0, 高度)   // 160ms 投影窗口
     在 [各档位移..., 高度] 里找距离 projected 最近的；若最近的正好是最后那个
     (= 高度) → 关闭；否则吸附到该档位移。
4. 恢复过渡（transition: ''）后再写新的 transform，让过渡从当前跟手位置接管。

硬要求：
- 档位位移必须**用到时现算**（高度 × (1 − 比例)），不要在初始化时缓存 ——
  节点在 display:none 状态下 offsetHeight 是 0，缓存会让面板永远停在全开档。
- 位移一律走 transform，不要动 top / bottom / height。
- 投影结果必须 clamp 到 0..高度。不钳的话往上狂甩会算出负落点。
- 有档位时遮罩**不要**跟手变淡。档位之间是稳态，跟手淡出会让最低档看起来像快关了。
  遮罩只在真正关闭时过渡到 0。
- 关闭 = 滑到 translateY(100%)，然后通知调用方隐藏节点；组件自己不要 remove 节点。
- 调用方传初始档位时，下标按"排序后的档位数组"数；实现内部必须自己 sort 一次。

验收：
- 从最低档慢慢往上拖 27% 高度（正好到中档）→ 停在 62%，位移 = 高度 × 0.38。
- 再慢慢往上拖 38% 高度 → 停在 0（全开）。
- 从全开慢慢往下拖 20% 高度 → 回到 62%（不是直接关）。
- 在最低档往下轻甩（约 0.5px/ms，只拖 70px）→ 面板关闭。
- 慢慢往下拖 25% 高度（从 62% 出发）→ 停在最低档，不关。
- 拖到任意位置派发 pointercancel → 滑回拖动前那一档，不关闭。
- 关闭后重新打开 → 回到调用方指定的初始档，且没有"先闪一下全开"。

别让它做的：
- 别用 height / max-height 做档位切换 —— 每帧重排，而且会打断内容滚动。
- 别把"拖得够远"和"甩得够快"写成两个并列的 if —— 它们要合成一个投影落点。
- 别在最低档只靠投影判断关闭 —— 最低档到关闭档隔着一整段高度，
  必须单独给"在最低档甩一把"开一条判定。
- 别给面板常驻 will-change: transform —— 拖动开始加、结束摘。
```
